# 0.3.0rc1 Release Candidate Design

## 背景

仓库的包版本和发布文档已经声明 `0.3.0`，`CHANGELOG.md` 也包含 dated
`0.3.0` 条目，但本地和远端都不存在 Git tag，因此该版本没有完成仓库定义的发布
流程。刷新远端引用后，当前开发分支相对 `origin/main` 包含 52 个后续提交，并缺少
`origin/main` 上的 1 个合并提交。

本次工作建立真正的预发布候选，而不是补打最终版 tag。Python 包使用符合 PEP 440
的版本 `0.3.0rc1`，Git 使用便于人类阅读的 tag `v0.3.0-rc.1`。

## 目标

- 通过专用 release 分支和 release pull request 审阅 `0.3.0rc1`。
- 让包版本、CHANGELOG、发布流程文档和 GitHub Release 状态一致。
- 在本地发布门禁和 GitHub required checks 全部通过后，只给合并后的 `main` 提交打
  `v0.3.0-rc.1` tag。
- 创建标记为 prerelease 的 GitHub Release，并以仓库中的 RC changelog 作为发布说明
  的事实来源。

## 非目标

- 不发布 `0.3.0` 最终版。
- 不上传包到 PyPI 或其他包索引。
- 不重写或压缩当前 52 个提交的历史。
- 不修改运行时行为、依赖版本或生成的 requirements 锁文件。
- 不把 `agent/` 的依赖或约定引入主包发布流程。

## 发布分支和历史

从当前已推送的 HEAD 创建 `codex/release-0.3.0rc1`，然后把最新
`origin/main` 合入该分支。合并仅用于记录 release 分支已包含目标分支的最新历史；
若出现内容冲突，停止发布准备并先解决冲突和重新验证，不通过 rebase 重写 52 个
候选提交。

release pull request 的目标分支是 `main`。不得在 release 分支 HEAD 上创建正式 RC
tag。pull request 通过 required checks 并合并后，重新获取 `origin/main`，确认合并
提交包含 release preparation commit，再在该 `main` 提交上创建 tag。

## 版本和发布记录

`pyproject.toml` 中 `[project].version` 从 `0.3.0` 改为 `0.3.0rc1`。运行时 API
版本和兼容性移除版本是独立版本轴，本次不修改。

`CHANGELOG.md` 保留 `Unreleased` 入口，但把没有真实 tag 支撑的 dated `0.3.0`
条目改为 `0.3.0rc1 - 2026-07-11`。RC 条目应覆盖原 `0.3.0` 内容以及候选范围内对
用户、运维和发布审核有意义的变化，至少包括：

- 服务、构建和 worker 入口及其运行时装配变化；
- answer failure copy 与公共 API 契约变化；
- 企业质量语料、离线门禁、真实依赖门禁和 live quality 证据；
- API 压测阈值、默认基线及失败时非零退出契约；
- 重要的安全、依赖审计、SBOM 和兼容性说明。

发布记录不逐条复制 52 个 commit subject，也不把生成报告中的敏感数据写入 release
notes。

## 发布流程文档

`docs/release_process.md` 增加预发布约定：

- Python 包版本 `0.3.0rc1` 对应 Git tag `v0.3.0-rc.1`；
- RC 必须通过 release pull request 和现有 required checks；
- tag 必须指向通过检查并合入 `main` 的提交；
- GitHub Release 必须标记为 prerelease；
- 最终版 `v0.3.0` 仍需独立执行完整发布流程，不能移动或复用 RC tag。

## 验证和产物

release preparation commit 在推送前必须通过：

1. `python scripts/local_gate.py`；
2. Python sdist 和 wheel 构建；
3. 从构建产物核对 distribution version 为 `0.3.0rc1`；
4. 检查工作树只包含预期的版本、changelog、流程文档和设计/计划变更；
5. 确认本地与远端不存在同名 `v0.3.0-rc.1` tag。

`dist/`、测试缓存和门禁报告属于本地产物，不提交。若本机缺少已有开发依赖所提供的
构建工具，先报告阻塞，不为本次 RC 临时增加生产依赖。

GitHub CI 必须满足 `docs/release_process.md` 中的 pytest coverage、incremental
coverage、mypy、Ruff、offline release gate、dependency audit、secret scan 和 SBOM
要求。保留 CI 生成的 `graph-rag-c9-sbom` artifact 供 release artifact review。

## 失败处理

- 任一本地门禁失败：不推送 release preparation commit，修复后从失败的最窄测试开始
  重跑，并最终重新运行完整 local gate。
- pull request required check 失败：不合并、不打 tag，修复必须留在同一 release PR
  中接受重新审核。
- tag 名已存在或指向错误提交：停止流程；禁止强制移动或覆盖 tag。
- 合并后 `origin/main` 不包含 release preparation commit：停止流程并调查目标分支，
  不在其他提交上补打 tag。
- GitHub Release 创建失败：保留已验证且不可移动的 tag，修复远端发布步骤后重试，不
  重建 tag。

## 完成条件

- `main` 包含经审核的 `0.3.0rc1` 版本和一致的发布文档。
- `v0.3.0-rc.1` 唯一存在，并指向通过 required checks 的 `main` 提交。
- GitHub 上存在与该 tag 对应且标记为 prerelease 的 Release。
- 本地和 CI 门禁结果已记录，SBOM artifact 已保留。
- PyPI 和其他包索引没有发生发布。
